0. Problem Statement (2 minutes, no clicking — just talk)
Before I walk you through the platform, let me explain the problem we're trying to solve.
 
Most COBOL apps have been running for years, but the knowledge is buried in the code. When a change request comes in, the hard part isn't making the change, it's figuring out the application.
 
Today, answering those questions often means spending hours through code or finding the person who knows the system.
That's what we're solving: making application knowledge easy to access and impact analysis much faster.
 
Let me walk you through the live demo."
 
 
1. Dashboard
Upload a COBOL application, including programs and copybooks, and the platform automatically parses everything, builds the call graph, extracts business rules, and creates a searchable knowledge base.
 
Connected Intelligence Score / Business Rules Captured / Applications Connected

Behind the scenes, the platform follows an agentic pipeline powered by LangGraph. 
Ingestion Agent – Discovers application files and parses the COBOL source code.
Analysis Agent – Extracts business rules, dependencies, CICS/SQL flows, batch jobs, and data flow relationships.
Knowledge Base Agent – Creates chunks, generates embeddings, and builds the searchable knowledge base.
Design Agent – Performs impact analysis and generates design drafts or reconciliation reports.
Query Agent – Answers user questions using only the knowledge extracted from the codebase.
"Together, these agents transform raw COBOL code into a connected intelligence layer."

3. Batch (JCL)
Most COBOL systems run through batch jobs.
This page shows the actual JCL entry points, which job runs which program, in which step.
That's critical for impact analysis because any program change, can affect downstream jobs.
 
4. Online (CICS)
"This is the online side, CICS transactions.
It shows which programs are real CICS entry points that a user can actually trigger from a screen, and program-to-program calls
 
5. Business Rules
For key programs, we generate a plain-English explanation of what the code actually does.
At the top is a business-level summary explaining the program's purpose.
Below that, we break the logic into individual business rules and explain each condition.
The Environment Summary shows how the program runs, whether it's batch or online, what data sources it uses, and its integrations.
Even someone with limited COBOL experience can quickly understand the program.
 
Dependency Graph
This shows the application's actual call graph generated from the source code.
 
Each node represents a program, with entry points highlighted so you can quickly see where execution starts.
You can filter the graph to focus on specific program relationships.
 
There's also a hierarchical view that shows how files and programs are connected across the application.
 
This gives you a quick visual view of how everything is interconnected, making impact analysis much easier.
One thing to note: everything you've seen so far comes directly from code parsing, not an LLM.
That keeps AI costs low and improves accuracy by using structured facts instead of assumptions.

8. Design Reconciliation
"This checks whether an existing design document still matches what the code actually does today.
You upload the document, select the program, and the system compares the documented rule against the Program
It flags three outcomes for every rule:
Covered – the document matches the code.
Conflict – the document says one thing, but the code does something different.
Missing – the code contains behavior that was never documented.
This helps identify stale documentation and undocumented logic.
